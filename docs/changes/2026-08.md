## CHG-012 — Normalize Secret-Scanner Paths Across Scan Modes

Date: 2026-08-26
Status: Implemented

Normalized every Gitleaks-reported path to a project-relative, slash-separated form inside the secrets adapter before an AEOS finding is constructed.

Why: `gitleaks dir` reports absolute filesystem paths while `gitleaks git` reports repository-relative paths. Two defects followed. Deduplication keys on path, so a single secret present in both the working tree and Git history produced two findings and doubled the reported critical count. Separately, absolute paths reached the JSON report, so the same project produced different reports on different machines, contradicting the deterministic reporting contract accepted in M4.

Evidence: reproduced with real Gitleaks 8.30.0 against a repository containing two committed secrets that were also present in the working tree. Before: four critical findings. After: two. The JSON report is now byte-identical when the same project is checked from two different filesystem locations; previously it differed.

Security: no change to redaction, blocking behavior, or exit codes. A planted secret still yields `AEOS-SEC-001`, severity CRITICAL, and exit code 3. A secret outside the project root retains its absolute path rather than being misreported as project-local.

Tests: added cross-mode deduplication regression, a report assertion that no in-project finding carries an absolute path, a normalization table covering relative, nested, absolute, dot-segment and empty inputs, an outside-root case, and an idempotence check.

Result: `gofmt`, `go vet ./...`, `go test ./...` and build all pass. `internal/findings` coverage rose from 0.0% to 95.2%; `internal/secrets` from 74.7% to 77.6%.

## CHG-015 — Resolve Repository Identity: Migrate Module Path to `Aeos-`

Date: 2026-08-26
Status: Implemented

Migrated the Go module path from `github.com/baa-211/aeos-cli` to `github.com/baa-211/Aeos-` across `go.mod`, all Go imports, and documentation.

Why: the module path must match the repository URL for `go get` to resolve, because the path is the fetch address rather than a label. The user elected to keep the existing remote `https://github.com/baa-211/Aeos-.git` rather than rename it, so the module moved instead.

Options considered: rename the repository to `aeos-cli` (zero code change, GitHub provides redirects) or migrate the module path (codebase-wide edit). The user chose to keep the repository.

Accepted consequence: the path contains an uppercase letter. The Go module proxy and local module cache case-encode uppercase characters, so the module is addressed on disk and via the proxy as `github.com/baa-211/!aeos-`. This is valid and supported; it is cosmetically unusual and appears in cache paths and proxy URLs. The trailing hyphen is likewise valid.

Reversal cost: renaming the repository after publication would require a second module-path migration and would break any consumer already depending on the current path. This decision is cheapest to revisit before the first push and expensive afterward.

Verification: `go mod init` accepts both candidate paths (tested empirically on Go 1.24.4). After migration, `gofmt` is clean, `go vet ./...` passes, `go test ./...` passes across all seven packages, the binary builds with `-trimpath`, and `aeos check` self-validates with exit 0 against pinned Gitleaks 8.30.0.

## CHG-017 — Reject Unknown Manifest Sections (Silent Security Downgrade)

Date: 2026-08-26
Status: Implemented
Severity: Critical

Unknown top-level sections in `aeos.yaml` were silently ignored. Misspelling `security` as `securty` disabled secret scanning entirely while AEOS reported `Result: PASS` with exit code 0 — with a live RSA private key present in the scanned directory.

This is the failure mode the project exists to prevent, occurring inside the tool itself, and it fails open. The path-normalization defect found the same day over-counted findings, which errs safe; this one under-reported to zero.

Fix: the manifest parser now rejects any top-level section outside the known set (`aeos`, `classification`, `project`, `security`) with a configuration error and exit code 4, and suggests the intended section for near-misses via Levenshtein distance. Permissive parsing of its own configuration is a vulnerability in a security tool, not a convenience.

Tests: regression test reproducing the exact `securty` scenario and asserting both rejection and suggestion; unknown-section rejection; a positive control confirming all specification sections still load and `SecretScanRequired` is set; suggestion table; edit-distance table. `internal/config` coverage 77.7% → 83.5%.

## CHG-018 — Canonical Delivery Pipeline and Stage Records

Date: 2026-08-26
Status: Implemented

Reconciled four competing pipeline vocabularies into one canonical eight-stage delivery model and recorded the decision in `ADR-004`: Intake, Design, Build, QA, Security, Compliance & Accessibility, Release, Report & Documentation.

The superseding is documented rather than silent: the earlier seven-phase, eleven-stage and eight-globe models each map forward onto the canonical set.

Added `docs/stages/` containing eight `STAGE` records. Each carries purpose, principles, protocol, entry criteria, an exit gate, and an append-only dated memory section seeded with real findings from this work rather than placeholder text.

Security boundary: stage records are data, never instructions. AEOS validates their structure, identity, references and freshness; it does not execute their contents or act on them. A component that read a Markdown file and performed the steps written in it would make repository content trusted, contradicting both `SECURITY.md` and `AGENTS.md`, and would let anyone able to open a pull request change what the tool does by editing prose. Autonomous execution, if ever built, belongs outside the deterministic core and must emit proposals for human approval.

No validator change was required: the records are discovered, indexed, checked for duplicate identifiers and reference-validated by existing code. Record count rose from 18 to 27.

## CHG-019 — M6 Dogfooding: First Findings

Date: 2026-08-26
Status: Implemented

Running AEOS against itself after adding the stage records produced a genuine CRITICAL finding: Gitleaks' `generic-api-key` rule matched a documentation passage where a cipher algorithm name followed the word `key`, reading the identifier as a high-entropy secret. AEOS behaved correctly by refusing to pass.

Resolved by rewording the documentation rather than adding a scanner allowlist. An allowlist would have silenced this finding and every future match of that rule — the mechanism by which real secrets eventually go unreported. Prose is cheap to change; a weakened detection rule is permanent and invisible.

A second instance appeared immediately: the memory entry written to record the first finding quoted the offending phrase and reproduced it. Documenting a false positive by quoting its trigger recreates the trigger. The entry now describes the pattern without reproducing it.

Open gap for the Preview UI: the JSON report exposes `schema_version`, `project`, `manifest_path`, `summary`, `findings` and `result`, but no record index. A UI rendering the eight pipeline stages from AEOS truth cannot currently do so from the report alone and would have to parse records itself — which would make it a second source of truth. Recorded as M6 work.
